# Six voters, stated — the v7.1 line and what each version after it claims

**Owner ruling, 2026-09-19: the 7th voter seat stays EMPTY.** The public backdrop is six voters —
10Y · VIX · F&G · CPI · CAPE · NFCI — and that is now a deliberate ceiling, not a count that
happens to be six. Everything else the feed carries is real and is integrated by ROLE.

## 1. Version build goals — the decision

Five planned slices map onto **three releases**, and the split is not arbitrary: each version
makes exactly one kind of claim, so a reader of the release notes can tell what moved.

| Version | Slices | What it claims | Model change? | Owner action? |
|---|---|---|---|---|
| **v7.1** | A · B · C | Six voters stated; every other factor integrated into Degen by role; Simple defined as fundamentals | **No** | **None** |
| **v7.1.5** | E | Release-aware CPI ingestion, freshness and display | No band moved; one stated behaviour change | **`wrangler deploy`** |
| **v7.2** | D | The Sahm bearish-only safety override | **Yes** | None |

> ⚠ **CORRECTED 2026-09-19, after v7.1.0 shipped.** This table originally scheduled CPI as
> **v7.3**, behind the Sahm override, on the reasoning that E needs a Worker deploy and D does
> not. The owner reordered it — *"build the cpi work to plan and version it 7.1.5"* — and the
> table is corrected in place rather than left standing, because a plan that keeps describing an
> order nobody followed is the label-outlives-its-data defect one level up. The reasoning that
> put E last still holds and is why the deploy is named at the top of the release notes; it was
> a ranking, not a dependency, and nothing in D blocks E or vice versa.

### Why v7.1 is A + B + C and not A + B alone

The owner's ask was *"be intentional about only 6 voters, but other factors are real and
integrated into degen mode"*. Slice A built the doctrine (the registry, the derived quorum) and
Slice B answered the stock-widget addendum. **Slice C is the "integrated into Degen" half.**
Shipping without it would leave the registry real but invisible: every non-voter would still be a
role-less leftover tile, which is the exact state the ask describes. A release whose title is the
owner's ask must contain the owner's ask.

All three are presentation and doctrine. No band moves, no `vote()` changes, nothing is inert on
deploy. That is one coherent release.

### Why the Sahm override is its own version

It can force the published call bearish. That is a **model change**, and this repo's precedent is
unambiguous: NFCI (v3.43) and the 30Y (v3.55) both arrived as non-voters specifically because
changing what moves the call deserves its own ruling, and FEAT-30Y-CHECK (v5.97.0) took a whole
version for one Engine 0 voter. Bundling it into a UI release would make the notes lie about what
moved. It also needs its own smoke section, three negative controls, and a check that
`validFrozenCall` does not enumerate the override vocabulary.

**Order matters: C before D.** Slice C's face renders the overrides (PANIC, Macro Flip, Sahm) with
distance-to-trigger. If D shipped first the new override would have only the `CallBanners` home
and would need re-siting a release later; with C first it slots into a block built for it.

### Why CPI is last, and what is inert until the owner acts

Slice E is the only one requiring an owner action. The release-day refresh arm is a Worker cron
change, so **the arm does not exist until `cd worker && npx wrangler deploy` runs** — the v6.2.0
precedent, where the owner action was named at the top of the notes rather than buried. Everything
else in E (calendar-month pairing, the release calendar, the month-words display) ships with the
Pages build and works immediately.

It is last rather than first because its live content is real but not urgent: the positional
pairing is a **latent** defect (CPIAUCNS publishes continuously, so the pairing is correct today
and wrong only when a month is suppressed), while the display confusion and the release-day
freshness hole are live but cosmetic and bounded. Slice C, by contrast, is the half of the owner's
ask that is currently missing.

### Not split further

E could be cut into "correctness + display" and "the cron leg", but that over-splits: v6.2.0
shipped surfaces and a cron together and simply stated the owner action clearly. One version, one
claim, with the inert half named at the top.

## 3. THE COUNT TRAP, measured

| voters | majority needs | quorum needed (old literal) | quorum needed (derived) |
|---|---|---|---|
| 6 | 4 (67%) | 4 (67%) | 4 (67%) |

backdrop never did. The quorum now computes the two-thirds rule its own comment always claimed.

## 4. THE COMPOSITION FINDINGS — recorded, not acted on (owner ruling 5)

Asked whether the current six are the *optimal* six, the owner's call was: **lock the count for
v7.1 and record the findings.** No band moved. These are measured claims with their evidence so
the next pass inherits numbers rather than rediscovering them.

### 4.1 Valuation is close to a permanently one-way voter

Its rule (`src/regime.js`, the `valuation` band):

```
bull  : CAPE < 26.1      (CAPE_MEAN 17.4 × 1.5)
bear  : CAPE > 30  OR  CAPE > 90% of the all-time high (44.19 → 39.77)
```

**Every fixture in the repo votes bear.** The mock baseline is 42.78 at 96.8% of its peak
(`src/mockData.js:66`); the full-live browser fixture is 31.2 (`test/public-render.mjs`); the only
bull fixture is a hand-made 19. Shiller CAPE last sat below 26.1 around 2013, so the bull side is
structurally unreachable in the current regime.

This repo has already ruled on exactly this shape. v3.43.1, re-banding NFCI: *"a factor that
always votes the same way does not inform a majority tally, it silently biases it."* NFCI's bands
were made asymmetric so the ordinary reading lands NEUTRAL. **Valuation never got that treatment.**

**⚠ Honest limit:** multpl.com is unreachable from this build environment, so the claim is that
the bull edge is structurally unreachable — **not** a counted vote distribution. Measuring that
needs a real CAPE history and is owner-side work.

### 4.2 Sentiment partly duplicates volatility

The F&G band's own explainer says so out loud (`src/regime.js`): *"Its inputs partly overlap
VIX."* CNN's composite includes a volatility component, so two of six votes share an input. That
is the v3.83 collinearity class — admitted in the copy, never measured.

### 4.3 The uncovered channel is growth

The six span rates · volatility · sentiment · inflation · valuation · plumbing. **Nothing reads
whether the real economy is expanding.** Unemployment and the Sahm rule are already computed and
already rendered, non-voting — which is precisely what makes v7.2's override the right home for
the growth channel *without spending a seat*.

### What would decide it

An owner ruling, not a measurement — the bands are asserted, not calibrated. The cheapest honest
next step is **4.1 alone**: re-band valuation asymmetrically the way NFCI was, so the seat can
abstain in ordinary conditions. That repairs the biased seat without a swap and without touching
the count.

## 5. Two defects found while answering the owner's mortgage question

Both were live, both are fixed in Slice A, and the second is the more interesting one.

1. **The housing row had no provenance at all** — the only row in the macro grid with no
   `SourceBox`, no mode and no as-of. A dead `MORTGAGE30US` feed rendered a mock 6.51% with a
   hand-written red and no badge: the v3.1 invariant, live on the page.
2. **The sweep that should have caught it was VACUOUS.** *"Every SourceBox in the macro grid
   passes an asOf"* compares SourceBox count against dated-SourceBox count — so a row with **no
   SourceBox at all** is not counted, not flagged, and reads as compliant. The v3.60.1 trap. The
   pin now asserts the SET of fields and names any that lack provenance; the control confirms it
   reports `missing: mortgage30` where the old one printed green.

**The ruling:** `mortgage30` is CONTEXT, never a voter. As a vote it fails the v3.43 moat test —
the 30-year mortgage is a spread over the 10-year the backdrop already votes on, so seating it
would cast two votes for one observation (the v3.83 collinearity defect, the TLT rejection in a
different wrapper). It earns its place as context because the *spread over the 10-year* is a
credit-transmission fact the 10-year alone cannot see, and that is what the row now states.

**No other housing data exists** in the product — no housing starts, permits, Case-Shiller,
home sales, mortgage applications, builder sentiment, REIT or homebuilder ETF. Adding one is a new
upstream and a new tile, and the seat question is already answered, so none is proposed.

### Where this note's own plan was WRONG, corrected rather than edited away

1. **The `macroCall.js:71` guard was already there.** The plan said to add `length >= 2` to the
   availability gate. Measured, that module's `series()` helper has required exactly that all
   along. The unguarded path was the **dashboard's** (`evidence.js` keys availability on field
   mode alone), and that is the one closed.
2. **The 70-day window's defect is a CRY-WOLF, not an over-tolerance.** The plan framed it as too
   permissive. Measured: CPI for month M is period-dated M-01 and remains the freshest published
   value for ~71 days, so the flat rule marks a **current** print stale for a day or two before
   every release and drops a voter. Release-awareness is therefore mostly a fix for false
   staleness, and detects a genuinely missed release a few days LATER than the flat rule did —
   the cheaper side of the trade, given the gate excludes a voter.
3. **"Fail open past the end of the calendar" was wrong.** It degrades to the flat rule instead.
   An expired calendar cannot say a release was missed, but a feed dead since 2019 must still
   read STALE, and failing fully open would have let one keep voting once the table ran out.
4. **`mockData`'s `nextRelease` was NOT pressed into service.** The plan called it "the natural
   carrier" for the next-release date. The arm reads `CPI_RELEASES` directly, because routing a
   schedule through a mock field would be a second home for it. The dead field stays dead and is
   named here rather than quietly repurposed.

### My own pins that were wrong on their first run

1. **The cron pin matched TEXT, so the control did not bite.** Disabling the arm with `false &&`
   left the suite fully green — the pin asserted `controller.cron === SNAPSHOT_CPI_CRON` as a
   string. The gate is exported (`cpiReleaseOn`) and RUN both ways now, and the dispatch is
   DRIVEN against a fake KV.
2. **Re-run, that control CRASHED the suite** instead of turning a pin red: a disabled arm falls
   through to the legacy FRED path, which throws on the absent key, and a run that dies mid-suite
   prints no total — which reads exactly like a suite that passed (v3.99.4). The drive is
   try/catch-guarded, so a fall-through is a RED assertion.
3. **A browser pin read the voter-sheet phrase off the wrong sheet.** The strip tile renders the
   band's raw `explain.what[1]`; the composed current-vs-reference bullet lives on the Simple
   CARD. The v7.0.3 split, measured again — and the tile's sheet is now pinned NOT to claim the
   phrase, so the pin cannot pass on whichever sheet happens to open.
4. **A trend-ordering pin read its direction off a synthetic ramp**, which proves the fixture
   rather than the ordering. Replaced with two hand-computed YoY values that differ.

### Honest limits, stated

- **`CPI_RELEASES` is ASSERTED, not owner-confirmed.** bls.gov is unreachable from this build
  environment (the same proxy 403 that made `FOMC_MEETINGS` an asserted table). The 90-day expiry
  tripwire forces the refill; `CPI_RELEASE_GRACE_D = 5` absorbs date error in the safe direction.
  Re-confirm against `bls.gov/schedule/news_release/cpi.htm`.
- **Reverting the snapshot wiring turns exactly ONE pin red** — the source pin. The behavioural
  pins run against `src/inflation.js` and cannot see a call site; `fetchFred` is not exported, so
  there is no end-to-end drive available. A function never called is functionally absent (v6.7.3),
  and that single pin is the whole guard at that seam.
- **The release rule detects a missed release later than the flat rule did** (release + 5 days
  versus ~70 days from the period start, which for CPI land close together). Named above.
