# 2026-08-28 — the 10am freeze did not write

Branch `claude/10am-freeze-write-failure-o9g2ss`. Working notes, not a product surface.

## Symptom

Prod, Fri 2026-08-28: `call_frozen: false`, no `captured_at`, snapshot still
`data pulled 08/28/2026 02:40 ET`. Thursday 8/27 froze normally (10:01 ET). Worker code
unchanged since 8/26.

Opening hypothesis (owner): either the `0 14 * * 1-5` branch did not run, or it ran and left
a `FAILED` row — POST /refresh not publishing, then the Worker's `readout.json` fetch also
dying. Stated as needing a KV read to split, because `_diag.cronLastWarm` is behind
`DEBUG_TOKEN`.

## What the public API showed (no KV read needed)

`functions/history.json.js` filters rows on `r && r.date` only — **not** on `capture_status`.
A `FAILED` row is a row and it renders with its `failure` string. So the public feed already
splits the two branches.

`GET /history.json` (cache-busted):

```
rows: 2026-08-27 CAPTURED · 2026-08-26 CAPTURED · 2026-08-25 CAPTURED
has 2026-08-28: False
```

**No 8/28 row of any status.** The capture `put` carries no `expirationTtl`, so it cannot
have aged out. That refutes "ran and left a FAILED row" outright.

It also exonerates the readout fetch. `captureDailyCall` is write-or-nothing past its
"already captured" guard: refreshed-call-present, `readout HTTP N`, bad schema and thrown
fetch all converge on the same `record` construction and the same `put`. A dead readout
writes `capture_status: "FAILED"`; it does not skip the row.

`GET /readout.json` at the time of investigation returned a healthy `md-call-v1`,
`effective_date: 2026-08-28`, BULLISH / FULL, `current: 5`, `missing: ["fed_next_meeting"]`.
So had the capture reached its `put`, it would have written a CAPTURED row.

### Correction to the opening hypothesis (Kalshi / publishIfNoWorse)

Two independent reasons it does not explain the miss:

1. `readoutQuality` is `[flip.evaluable, current_panic_gauges, current, usable, -historical,
   -missing, asOfEpoch]`, compared lexicographically. **Kalshi was already missing from the
   incumbent 02:40 snapshot**, so it cancels out — it cannot make a 10am candidate "worse"
   than a snapshot equally without it. With the first six equal, `compareQuality` falls to the
   `asOf` tiebreak and the candidate publishes. A completed refresh would have moved `as_of`
   off `06:40:33.541Z`. It did not.
2. Even if the candidate *had* been strictly worse: `published:false` → `call:null` → capture
   falls to the readout fetch → healthy readout → **CAPTURED row**. Still a row.

`?fresh=1` was also checked and is not a rebuild — it only sets `noStore`; the handler reads
KV first (measured ~0.7s on a hit).

## Root cause (owner, from the Cloudflare Triggers panel)

**The Cloudflare dashboard treated `1-5` as Sun–Thu, so Friday never fired.** All four
triggers carried a numeric day-of-week. Under a Sun–Thu window:

| date | day | expected | observed |
|---|---|---|---|
| 2026-08-25 | Tue | fires | CAPTURED |
| 2026-08-26 | Wed | fires | CAPTURED |
| 2026-08-27 | Thu | fires | CAPTURED |
| **2026-08-28** | **Fri** | **skipped** | **no row at all** |

That matches the evidence exactly, and it is the one explanation consistent with *no row*
rather than a FAILED row: the branch never ran, so nothing reached the `put`.

Numeric day-of-week is off-by-one between cron implementations. `MON-FRI` is unambiguous in
all of them, so the fix is correct regardless of which side's numbering is "right".

**Residual, stated rather than smoothed:** Mon 2026-08-24 has no row either, which a Sun–Thu
window does not explain (Monday would be inside it). The likely reason is the deploy date —
`/history.json` reports `history_start: 2026-08-25` and the feed is live-forward only — but
that was not verified. It does not affect the Friday diagnosis.

**Not independently verified here:** the Cloudflare-side interpretation itself. That is the
owner's read of the Triggers panel; this branch corroborates it from the history feed only.

## What changed

Day-of-week only. Hours untouched (12:00, 12:30, 14:00, 21:00 UTC).

- `worker/wrangler.toml` — all four triggers `* * 1-5` → `* * MON-FRI`, plus the DST variants
  and the "weekdays only" gloss. New ⚠ comment at the cron array recording that the dashboard
  treated `1-5` as Sun–Thu, that this cost Fri 2026-08-28, and that "Next run" must read
  MONDAY after every deploy.
- `worker/cron.js` — `SNAPSHOT_WARM_CRON` and `SNAPSHOT_PREWARM_CRON` (and their EST
  variants in comment) moved to `MON-FRI`. Dispatch is exact-string match, so these had to
  move with the TOML or both snapshot jobs would fall through to the legacy FRED path.
- `worker/SETUP.md` — the trigger table, the two `wrangler dev` simulation curls, and the
  twice-a-year DST block. The DST block is what an operator pastes in November; leaving `1-5`
  there would have reintroduced the bug at the next time change.
- `test/smoke.mjs` [67] — two new pins plus the legacy-cron literals moved to `MON-FRI`.

### Pins

- `crons: the DOW field is NAMED everywhere` — `wrangler.toml` contains `0 14 * * MON-FRI`,
  and no `* * 1-5` (or the URL-encoded `*+*+1-5`) survives in `wrangler.toml`, `cron.js` or
  `SETUP.md`.
- `crons: every TOML trigger names its weekdays` — derived from the parsed cron array, so a
  fifth trigger added later cannot slip in numeric.

Negative-controlled: reverting one trigger to `0 14 * * 1-5` turns 5 assertions red — both
new DOW pins, and three pre-existing reconciliation pins (the constant is orphaned, the
fallthrough count changes, SETUP.md stops matching). The regression is silent in production —
a wrong DOW does not fail a deploy, it just skips a day — which is why it is pinned in both
directions across every surface an operator copies from.

Gates: **2050 smoke · 306 render · 196 public-render · `audit:prod` clean.** Browser suites
run in real Chromium (`npm install` had not been run in this environment — the v3.69 trap
where `test:ui`/`test:public` skip cleanly and read as passes).

## Open / deferred

1. **Owner verification step, still outstanding:** after `npx wrangler deploy`, the Triggers
   panel must show each cron's *Next run* as a **Monday**, not Sunday 30 Aug. Nothing in this
   repo can assert that — it is Cloudflare-side state.
2. **The 10am freeze remains a single-shot KV write with no retry.** The reverted catch-up
   would also have covered an evicted invocation or a failed `put`. Worth reconsidering as its
   own scope once the DOW fix is confirmed by a Friday that actually freezes.
3. **`warmSnapshot` still returns before `recordWarm`** on the "already warm" path, so
   `pulse:cron:lastwarm` is silent on exactly the days the prewarm correctly skips. That
   blind spot is part of why this incident was not diagnosable from the marker alone.
4. **A brittle assertion in `test/smoke.mjs`** (`hist.rows[0].call.headline`, [73]) throws a
   TypeError instead of failing legibly when a record is rewritten to `call: null`, killing
   the run with no total printed — the v3.99.4 P0 shape. Only reachable under a deliberately
   broken immutability guard. Left alone to keep this pass surgical; a one-character `call?.`
   fixes it.
5. `pulse:refresh:attempts` (30-day rolling log, written by `/api/snapshot/refresh` itself) is
   more informative than `pulse:cron:lastwarm` for this class of question and is read by
   nothing. If the Friday freeze still misses after this deploy, that is the read:
   `npx wrangler kv key get --remote --namespace-id=78ad3346a8fe4757a906283c4bc81a5e "pulse:refresh:attempts"`

## Outcomes

- Root cause identified as the numeric day-of-week; fix applied to all four triggers across
  the four surfaces that must agree (TOML, `cron.js` constants, SETUP.md, smoke).
- The public `/history.json` feed — not a KV read — is what split "never ran" from "ran and
  failed". Worth remembering: the accountability feed publishes FAILED rows, so *absence of a
  row* is itself a specific, readable signal that the branch never reached its write.
- Gates green; two pins added and negative-controlled.
- Not yet closed: the deploy and the Triggers-panel confirmation (item 1 above).

## What this rules out

- Not a copy bug. Not Clock+Whys (merged after 11:04 ET observation).
- Not `publishIfNoWorse` rejecting a 10am candidate — that path never ran, because the
  Worker was never invoked.
- Not a FAILED history row from a botched capture — capture never ran.
- 8am prewarm skip-if-warm is irrelevant: the 8am cron itself has no Friday event.

The freeze did not land because **the 10am cron did not fire today**.
